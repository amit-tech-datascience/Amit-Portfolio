Incident Lab: investigating ML service failures

An evidence-first AI workbench that compares rules and model hypotheses, preserves failed attempts, and makes recovery testable.

Statusv0.3.2 delivered · source and demo private

Tools & methodsPython, FastAPI, SQLite, OpenTelemetry, LLM evaluation, GitHub Actions

The problem

An incident explanation can sound convincing while mixing services or citing evidence that does not support the diagnosis. Engineers need to inspect the observations, understand uncertainty and recover safely when a provider or worker fails.

From observation to review

  2. Bounded investigationRules baseline plus one model call; omissions disclosed.
  3. Validated reportSupported citations, source-rendered facts and visible failures.

Architecture summary, not a live investigation.

My contribution

I designed and built a local investigation workbench, a separate durable worker, a controlled fault-injection lab and a frozen evaluation workflow. This is solo, AI-assisted engineering: architecture decisions, implementation, failure analysis and delivery, with independent human review still pending.

The approach

The application validates immutable observation snapshots, compares a rules baseline with a bounded model call, and checks the returned categories and citations. The model selects hypotheses and references; application code renders factual statements from the cited records. A separate controller and evaluator retain fault labels outside investigator input.

Results & learning

The v0.3.2 delivery passed 134 Python tests, JavaScript checks and clean Windows/Linux CI, including wheel installation outside the checkout. The portable demo preserves 36 synthetic observation windows and 72 saved report attempts: 64 completed and eight failed. Saved playback needs no provider key.

Architecture decisions

  • A modular backend and one worker. FastAPI and SQLite keep state transitions inspectable. Leases fence stale writes; idempotency links duplicate submissions to the same job. This is a local persistence boundary, not distributed availability.
  • A bounded model contract. Provider input is limited to 40 records and 10,000 serialized characters. Fixed signal mappings and opaque aliases replace raw log text. Groq was tested live; OpenAI remains an optional adapter without live verification.
  • Evidence before fluent narration. Schema, citation and domain-support checks reject unsupported outputs. Exact observation values and timestamps come from source records. Citation correctness does not prove causality.
  • Recovery without silent retries. HTTP 429 retains the failed attempt and persists a provider cooldown. Later queued work waits; rules can progress. Cancellation, process restart, backup/restore and unfinished-job quarantine are exercised with simulated providers.
  • A separate evaluation boundary. A fault controller exercises an OpenTelemetry workload and a small trained ML service over HTTP. Scenario labels stay with the evaluator. The host worker does not inherit the separate rules container’s network isolation.

What the demonstration shows

  1. Compare a saved ML contract-mismatch report with the rules baseline and follow a factual claim to its cited observation.
  2. Inspect a healthy or recovery control that abstains, then open a failed attempt and its safe diagnostic category.
  3. Run a simulated cooldown drill: retain the original 429, complete rules during the hold, cancel queued work and resume one later job after expiry.
  4. Restore a verified backup and explain the boundary between a saved replay, a simulated operational test and a fresh provider call.

Source and the portable release are private. A walkthrough is available on request; this public page is an editorial case study, not a hosted app or a public download. The demo includes no provider credentials, raw telemetry or employer data. No live model call is made by this website.

Verified delivery

Clean Windows and Linux CI passed for release source c28f5be. Package installation, browser playback, backup restoration and the mock cooldown drill were checked. The original evaluation files and v0.3.0 bundle remained unchanged. Independent review is the next gate, not another feature milestone.

What this establishes

A local, single-user research workbench, not a production incident responder. Evaluations cover small, known synthetic failure families; controls include abstentions. The model has not demonstrated an advantage over the rules baseline. Shared support predicates constrain both approaches. Independent technical review and a physical second-PC check are deferred. No team-management experience is claimed.
